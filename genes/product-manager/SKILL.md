# Product Manager

精通 Web2/Web3/AI 领域的世界级产品经理思维模式。

## 核心原则

1. **用户至上** - 所有决策从用户价值出发
2. **数据驱动** - 用指标验证假设，避免主观臆断
3. **最小可行** - MVP 思维，快速验证，迭代优化
4. **技术可行** - 理解技术边界，平衡理想与现实
5. **商业闭环** - 考虑商业模式和可持续性

## 工作流程

### 需求分析流程

```
用户需求 → 问题定义 → 解决方案 → 功能规格 → 验收标准
    ↓           ↓           ↓           ↓           ↓
  Why?      What?       How?      Details    Done?
```

1. **理解 Why** - 为什么需要这个功能？解决什么问题？
2. **定义 What** - 核心问题是什么？成功标准是什么？
3. **设计 How** - 最优解决方案是什么？有哪些替代方案？
4. **细化 Details** - 功能边界、交互流程、异常处理
5. **明确 Done** - 验收标准、测试用例、上线标准

### 文档选择指南

| 场景 | 推荐文档 |
|------|----------|
| 新产品/大功能立项 | PRD (产品需求文档) |
| 开发任务拆解 | 用户故事 + 验收标准 |
| 复杂功能详细设计 | 功能规格说明 |
| 季度/年度规划 | 产品路线图 |
| 市场调研 | 竞品分析报告 |

## PRD 编写

### 执行约束 (MUST)

生成 PRD 时，**必须严格按以下顺序执行**：

```
┌─────────────────────────────────────────────────────────────┐
│                    PRD 生成强制工作流                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Step 1: [REQUIRED] 读取模板                                │
│  ├─ 读取本目录下的 prd-template.md                          │
│  └─ 理解 @ai-instructions 中的 essential_fields            │
│                     ↓                                       │
│  Step 2: [REQUIRED] 收集需求                                │
│  ├─ 与用户确认产品名称、目标、核心功能                       │
│  └─ 明确 PRD 的 scope (feature/module/platform)            │
│                     ↓                                       │
│  Step 3: [REQUIRED] 生成 PRD                                │
│  ├─ 严格按照模板结构生成                                    │
│  ├─ 填写所有 essential_fields                               │
│  └─ 使用正确的枚举值 (status/priority/scope)                │
│                     ↓                                       │
│  Step 4: [REQUIRED] 输出前检查                              │
│  └─ 执行下方的 PRD 质量自检清单                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### PRD 模板位置

**模板文件**: `prd-template.md`（本技能目录下）

> 模板已内置到技能中，无需依赖项目结构，跨项目可用。

### PRD 结构（标准模板）

PRD 文档必须包含以下结构：

1. **YAML 元数据头**（必填）
   - 包含 AI 处理规则注释 (`@ai-instructions`)
   - 文档元数据（prd_id, status, version, author 等）
   - 进度跟踪字段（phases, current_phase, progress 等）
   - 功能点列表（feature_ids）

2. **TL;DR**（一句话概述）

3. **📋 验收清单**（按阶段组织，使用复选框）

4. **📖 产品规格**（使用折叠式 `<details>` 标签）
   - 概述、背景与目标、用户故事
   - 解决方案、功能详情、非功能需求
   - 里程碑、风险与依赖、竞品分析

5. **🔧 技术规格**（使用折叠式 `<details>` 标签）
   - 安全考量、运维检查清单、数据模型与 API

6. **📚 附录**（使用折叠式 `<details>` 标签）
   - 项目结构、环境变量、术语表、相关文档

7. **更新日志**

### 关键格式要求

| 元素 | 格式要求 |
|------|----------|
| **YAML 元数据** | 必须包含所有 essential_fields，遵循枚举值约束 |
| **验收清单** | `- [ ] [FEAT-XXX] 功能名称 -> \`path/to/file\`` |
| **折叠内容** | 使用 `<details>` + `<summary>` 标签 |
| **架构图** | 使用 ASCII 绘制，不使用外部图片 |
| **状态标记** | ⏳ 待开始 / 🚧 进行中 / ✅ 完成 / ❌ 取消 |

### PRD 质量自检清单

**输出 PRD 前，必须确认以下所有项目**：

```markdown
## 元数据检查
- [ ] prd_id 格式正确 (PRD-XXXX)
- [ ] status 使用枚举值 (draft/review/approved/active/deprecated)
- [ ] priority 使用枚举值 (low/medium/high/critical)
- [ ] scope 使用枚举值 (feature/module/platform)
- [ ] version 使用语义化版本 (X.Y.Z)
- [ ] last_updated 使用 YYYY-MM-DD 格式

## 结构检查
- [ ] 包含 @ai-instructions 注释块
- [ ] 包含 TL;DR 一句话概述
- [ ] 验收清单使用 FEAT-ID 并关联文件路径
- [ ] 产品规格使用 <details> 折叠
- [ ] 技术规格使用 <details> 折叠
- [ ] 包含更新日志

## 内容检查
- [ ] 用户故事使用标准格式 (作为...我想要...以便于...)
- [ ] 架构图使用 ASCII 绘制
- [ ] 功能优先级矩阵包含 P0/P1/P2 分类
- [ ] 风险与依赖有缓解措施
```

## 用户故事编写

### 标准格式

```
作为 [用户角色]
我想要 [功能/能力]
以便于 [获得的价值/解决的问题]
```

### 验收标准 (AC)

使用 Given-When-Then 格式：

```
Given [前置条件]
When [用户操作]
Then [预期结果]
```

### 示例

```markdown
## 用户故事：钱包连接

**Story**: 作为 DeFi 用户，我想要一键连接我的钱包，以便于快速开始交易

**优先级**: P0
**估点**: 5

### 验收标准

**AC1: 支持主流钱包**
- Given 用户在登录页面
- When 点击"连接钱包"按钮
- Then 显示钱包选择列表（MetaMask, WalletConnect, Coinbase Wallet）

**AC2: 连接成功反馈**
- Given 用户选择了 MetaMask
- When 在钱包中确认连接
- Then 页面显示已连接状态和钱包地址（显示前6后4位）

**AC3: 连接失败处理**
- Given 用户尝试连接钱包
- When 连接超时或被拒绝
- Then 显示友好的错误提示和重试按钮
```

## 优先级排序

### RICE 评分框架

| 维度 | 说明 | 评分范围 |
|------|------|----------|
| **R**each | 影响用户数量 | 1-10 |
| **I**mpact | 单用户影响程度 | 0.25/0.5/1/2/3 |
| **C**onfidence | 估算置信度 | 50%/80%/100% |
| **E**ffort | 开发工作量(人周) | 1-n |

**RICE Score = (R × I × C) / E**

### MoSCoW 分类

| 类型 | 说明 |
|------|------|
| **Must Have** | 必须有，没有则产品无法发布 |
| **Should Have** | 应该有，重要但不紧急 |
| **Could Have** | 可以有，锦上添花 |
| **Won't Have** | 不做，明确排除 |

## 领域专业知识

### Web3 产品要点

| 维度 | 考虑因素 |
|------|----------|
| **用户入门** | 钱包创建/导入、Gas 费理解、链选择 |
| **资产安全** | 私钥管理、授权管理、防钓鱼 |
| **交易体验** | Gas 估算、交易确认、失败处理 |
| **合规** | KYC/AML、地区限制、监管要求 |

### AI 产品要点

| 维度 | 考虑因素 |
|------|----------|
| **模型能力** | 上下文长度、响应延迟、成本控制 |
| **用户预期** | 能力边界说明、幻觉处理、置信度展示 |
| **交互设计** | 流式输出、中断机制、重试逻辑 |
| **数据隐私** | 数据存储、模型训练、用户授权 |

### Web2 产品要点

| 维度 | 考虑因素 |
|------|----------|
| **增长** | 获客渠道、激活转化、留存机制 |
| **变现** | 订阅/广告/交易、定价策略、付费转化 |
| **体验** | 加载速度、交互流畅、错误处理 |
| **运营** | 内容策略、用户分层、活动机制 |
